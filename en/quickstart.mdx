## A · the library {#a--the-library}

The resolver uses a lexical index over LOINC, with numpy as its only dependency.
It needs no model, API key or database. With [uv
installed](https://docs.astral.sh/uv/getting-started/installation/), try it without
cloning the repository or managing a Python environment:

```bash
uvx --python 3.12 mirobody resolve "LDL cholesterol" 血红蛋白 ヘモグロビン "空腹血糖(GLU)" 血脂
```

uv downloads Python if needed and prepares the package in an isolated
environment. The initial download needs a network connection; name and unit
resolution then work offline. `--python 3.12` selects a supported interpreter.

<p align="center">
<img src="/images/oss/docs/images/resolve-demo.gif" alt="mirobody resolve: 血红蛋白 and ヘモグロビン landing on the same LOINC code, and one deliberate abstention" width="880" />
</p>

`血脂` names a category rather than one observation, so it resolves to nothing.
That is the design: a wrong code puts two different tests on one trend line.

For your own Python 3.12+ environment, install the library:

```bash
pip install mirobody
```

The same engine works from Python. The unit is part of a reading's identity,
so it can change the code:

```python
from mirobody.engine import resolve, resolve_reading, standardize_reading

resolve("血红蛋白").loinc                                     # '718-7'   any language, one code
resolve("total cholesterol").loinc                          # '2093-3'  [Mass/volume]
resolve_reading("total cholesterol", "5.0", "mmol/L").loinc  # '14647-2' [Moles/volume]: the unit picks the code
resolve_reading("中性粒细胞", "62 %", None).loinc              # '26511-6' a percentage...
resolve_reading("中性粒细胞", "4.2", "10*9/L").loinc           # '26499-4' ...and a count are two codes
standardize_reading("血红蛋白", "13.5", "g/dL")["code"]["coding"][0]["code"]  # '718-7'  as a FHIR Observation
```

Complaints and diagnoses have their own axis, ICPC-3, with the same rule: a
code or a stated refusal, never a guess.

```python
from mirobody.translate import resolve_symptom, resolve_condition

resolve_symptom("头疼").code           # 'NS01'         Headache; 'headache' and '頭痛' answer the same
resolve_symptom("疼").outcome         # 'refused'      too broad to code; the words are kept
resolve_condition("2型糖尿病").code    # 'TD72'         Type 2 diabetes mellitus
resolve_condition("糖尿病").outcome    # 'needs-input'  which type? asked, not assumed
```

Reading a vendor export needs nothing further; `zipfile` and `xml.etree` are
both stdlib:

```bash
mirobody import apple ~/Downloads/export.zip
```

For the rest: `pip install 'mirobody[parse]'` turns a PDF, photo or
spreadsheet into readings (that one calls a model, so it needs a key), and
`pip install 'mirobody[app]'` installs the server. Neither is needed for the
above. `[agent]` is the agent harness as a library, `[test]` the test suite.

Without the stack, `uvx --python 3.12 mirobody mcp` serves the vocabulary to
an MCP client over stdio, offline and with no key. Its one tool that reads a
whole document, `standardize_report`, also needs the `[parse]` extra and a
model key. [standardization.md](/en/concepts/indicators) covers ② Translate in
depth, and [`examples/`](https://github.com/thetahealth/mirobody/blob/4ed28c160af9ae0bede547880759e5570b2243df/examples/README.md) has runnable scripts.

## B · the stack {#b--the-stack}

The full app includes the web client, Postgres with pgvector, the server and
the worker, with a synthetic demo record already seeded. Choose where to run it.

### Try it in Codespaces {#try-it-in-codespaces}

[![Open in GitHub Codespaces](https://github.com/codespaces/badge.svg)](https://codespaces.new/thetahealth/mirobody?quickstart=1)

Create the codespace with your GitHub account; no local Docker or Python
installation is needed. Wait for automatic setup to finish in its terminal,
then open the HTTPS setup link it prints. Enter your own model API key, such
as [OpenRouter](https://openrouter.ai/keys) or
[OpenAI](https://platform.openai.com/api-keys). The setup page checks the key
with a real request before saving it. The app uses private forwarded port
`18060` by default.

Sign in as `you@mirobody.ai`, code `111111`, on the Email code tab and ask
"How has my cholesterol changed?" Upload a synthetic sample from
[`demo/upload/`](https://github.com/thetahealth/mirobody/tree/4ed28c160af9ae0bede547880759e5570b2243df/demo) on the Data page to try document processing.

The app and stored records are in GitHub's cloud, and documents and questions
sent for model processing go to your model provider. Use the included
synthetic data for the trial. [Codespaces usage and
billing](https://docs.github.com/en/billing/concepts/product-billing/github-codespaces)
and your model provider's charges apply. Stop the codespace when you finish;
reopening it runs the deployment script again to bring the app back up.

### Run it 100% locally {#run-it-100-locally}

No model API key is needed. Docker with Compose starts both the app and
llama.cpp's CPU service, which runs the answering model and document reader:

```bash
git clone --depth 1 https://github.com/thetahealth/mirobody.git && cd mirobody
COMPOSE_PROFILES=local-cpu ./deploy.sh
```

Allow 16 GB of memory, at least 8 GB of it for Docker. No GPU is required;
Windows users should run the commands in a WSL 2 terminal. The first start
downloads container images and model weights. Once downloaded, the app,
models, records and document processing all stay on your machine. CPU answers
can take minutes; [local-models.md](/en/local-models) has GPU and Mac options.
Open the app link the script prints and use the demo account below.

`deploy.sh` writes a `.env` with generated secrets and pulls the prebuilt
image, which already contains the LOINC bundle, so Docker users need no Git
LFS. It needs Git and OpenSSL on the host. The local profile selects the local
models automatically.

**To run Docker with a cloud model instead**, use `./deploy.sh` without a
local profile. Open the setup link it prints on `http://localhost:18060` and
paste one model API key. The app and records stay on your host; the model
provider processes the documents and questions sent to it.

Sign in as `you@mirobody.ai` with code `111111` on the Email code tab; no mail
provider is involved. `SEED_DEMO_DATA` is on, so 2,019 readings across two
accounts are already there. Set it to `false` before the first start if you
intend to hold real data, and neither account is created. Four files in
[`demo/upload/`](https://github.com/thetahealth/mirobody/tree/4ed28c160af9ae0bede547880759e5570b2243df/demo) are deliberately not seeded, so dropping one on the
Data page walks the real path.

A key can also go in `.env` instead of the setup page: `OPENROUTER_API_KEY`,
`OPENAI_API_KEY`, `GOOGLE_API_KEY`, `ANTHROPIC_API_KEY`, or any
OpenAI-compatible gateway through `<PROVIDER>_BASE_URL`. Run
`docker compose up -d` afterwards; a `restart` does not reread `.env`.
[`config.llm.yaml`](https://github.com/thetahealth/mirobody/blob/4ed28c160af9ae0bede547880759e5570b2243df/config.llm.yaml) names the variable each entry reads
(`api_key: OPENROUTER_API_KEY`), never the secret. To see what each model
surface selected:

```bash
docker compose exec mirobody mirobody doctor          # add --probe to send each a real request
```

[The self-host guide](/en/self-host) goes step by step,
and [walkthrough.md](/en/walkthrough) tours the running stack.

## C · a checkout {#c--a-checkout}

`serve` is the deployment shape: it reads the shipped config and any
`config.{ENV}.yaml` overlay, and expects persistent secrets. `dev` runs the
same server in one process with an in-memory config and generated secrets:

```bash
git clone --depth 1 https://github.com/thetahealth/mirobody.git && cd mirobody
git lfs install && git lfs pull
python3.12 -m venv .venv && . .venv/bin/activate
pip install -e '.[app]'
```

If you do not already have Postgres with pgvector, start one first:

```bash
docker run -d -p 5432:5432 -e POSTGRES_USER=user -e POSTGRES_PASSWORD=pw \
    -e POSTGRES_DB=mirobody \
    pgvector/pgvector:pg17
```

**`docker` is not required for that part.** On Debian or Ubuntu,
`scripts/install_native.sh` installs PostgreSQL and pgvector from the
distribution's own repositories, starts the cluster, creates the role and the
database, and puts the package in a virtualenv. Measured on Ubuntu 24.04, where
pgvector is 0.6.0 and satisfies the `CREATE EXTENSION vector` above.
`scripts/start_native.sh` then starts the worker and the server on port 18060,
and prints where to open it.

Then start the API, replacing the connection URL if you use an existing
database. Check its health endpoint from another terminal:

```bash
mirobody dev --pg-url postgres://user:pw@localhost:5432/mirobody
```

```bash
curl -fsS http://127.0.0.1:18090/api/health
```

The response includes a `version` field. Use pgvector rather than plain
Postgres: the schema creates a vector column on first start.

**Run `dev` from the repository root and it serves the web client as well.**
The built client lives at repo-root `frontend/`, outside the package, so it is
there in a checkout and absent from a `pip install`. `utils/config/http.py`
mounts `frontend/` whenever that directory exists in the working directory, so
one address then answers for the API, the MCP surface, the agent and the UI.
This page said the opposite until it was measured: from the repository root,
`GET /` returns the built page, and only a `pip install` outside a checkout
gets the API alone.

The secrets `dev` generates are per-run: sessions and encrypted config values
do not survive a restart. Set `JWT_KEY` and `CONFIG_ENCRYPTION_KEY` in the
environment to keep them.

## When it does not come up {#when-it-does-not-come-up}

| What you see                                                        | What it is                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `keys present : none` and every surface `--` from `mirobody doctor` | No model key and no local model server. ① Collect and ② Translate still work; extraction and answers do not. Open the link `./deploy.sh` printed.                                                                                                                                                |
| A LOINC lookup raises on a fresh clone                              | `git lfs pull` has not run, so the bundle is still a pointer stub.                                                                                                                                                                                                                               |
| `mirobody dev` exits asking for a Postgres                          | `--pg-url`, or `PG_URL` / `DATABASE_URL` in the environment.                                                                                                                                                                                                                                     |
| The server starts but device sync never runs                        | Check the worker logs and Postgres connection; device pulls and task state both use Postgres.                                                                                                                                                                                                    |
| `mirobody serve` cannot connect to Postgres                         | Set `PG_HOST`, `PG_PORT`, `PG_USER`, `PG_PASSWORD` and `PG_DBNAME` for that database.                                                                                                                                                                                                            |
| Image pulls hang, or `deploy.sh` reports Docker Hub unreachable     | `deploy.sh` tests the daemon's access to the registry and, when it fails, writes `DOCKER_MIRROR=<registry>/` into `.env` so the retry goes through a mirror, saying so as it does. Set the same key by hand to name your own; it prefixes every image, the base image of a local build included. |
