The Docker stack is the complete product: the web app, a Postgres with your record, a background worker, and a synthetic demo record to try it on. It needs Docker with Compose; on Windows, run the commands in a WSL 2 terminal. No Python, Node.js or GPU is required. The engine is open source under Apache 2.0 at [thetahealth/mirobody](https://github.com/thetahealth/mirobody).

## First answer in three steps {#first-local-result}

<Steps>
  <Step title="Start the stack">
    ```bash
    git clone --depth 1 https://github.com/thetahealth/mirobody.git && cd mirobody
    ./deploy.sh
    ```

    The script writes the secrets into `.env` (it needs OpenSSL for that), pulls the application image, creates the demo accounts and readings, and prints a link to the setup page.
  </Step>
  <Step title="Choose a model">
    Open the printed link and paste one model key: OpenRouter, OpenAI, Gemini, Anthropic, DeepSeek, DashScope, or any OpenAI-compatible gateway. The key is kept only after one real request through it works, and is stored encrypted; **Settings › Model** changes it later, without a restart. To keep every model on this machine instead, see [Where the models run](#models).
  </Step>
  <Step title="Sign in and ask">
    Open <Fact k="url" code /> and sign in as `you@mirobody.ai` with code `111111` on the Email code tab. Ask "How has my cholesterol changed?": the answer charts the trend and names the file behind each number. Then upload a file from `demo/upload/` on the **Data** page, or switch to the record `mom@mirobody.ai` shares with you.
  </Step>
</Steps>

The [walkthrough](/en/walkthrough) follows the same record through five scenes. For real records, apply the settings in [Deploy on a Server](/en/deployment/production) **before the first start**; after a demo, follow the [existing-demo path](/en/deployment/production#after-a-local-demo) to start with clean data volumes.

<AccordionGroup>
  <Accordion title="Check the services">
    From the engine checkout:

    ```bash
    docker compose ps
    curl -fsS http://localhost:18060/api/health
    docker compose exec mirobody mirobody doctor
    ```

    The `mirobody` service should be `healthy`, and the health response includes `version` and `agent`. `mirobody doctor` names the entry each model surface selected; `--probe` sends each a real request. A key added to `.env` later takes `docker compose up -d`; `docker compose restart` does not re-read `.env`. [Troubleshooting](/en/troubleshooting) lists the common failures.
  </Accordion>
  <Accordion title="No Git on this machine">
    The source tarball is the same checkout:

    ```bash
    curl -L https://github.com/thetahealth/mirobody/archive/refs/heads/main.tar.gz | tar xz && cd mirobody-main
    ```
  </Accordion>
</AccordionGroup>

## Where the models run {#models}

| | A model key | 100% on this machine |
| --- | --- | --- |
| Who runs the models | The vendor whose key you paste | [llama.cpp](/en/local-models)'s `llama-server`, beside the stack or on the host |
| You need | Docker and one key | Docker and 16 GB of memory for the default size, at least 8 GB of it for Docker |
| Speed | Set by the vendor and the model you choose | About 30 s on a 16 GB Apple-silicon laptop's GPU; minutes on a CPU alone |

To run the models in Docker beside the stack, start it with a Compose profile instead of the plain `./deploy.sh`:

```bash
COMPOSE_PROFILES=local-cpu ./deploy.sh     # any computer, no GPU
COMPOSE_PROFILES=local ./deploy.sh         # an NVIDIA GPU
```

The script points Mirobody at the model service, so the setup page has nothing to ask; the first question waits for a one-time download of about 3 GB. Without a GPU a first answer takes 2–3 minutes on an Apple-silicon laptop's cores and up to about 15 on a 4-vCPU x86 server. On a Mac, `llama-server` runs natively on the GPU and the setup page finds it. [Run Locally](/en/local-models) has every platform, the two sizes and what each needs; [Choosing a Model](/en/model-choice) compares them with five cloud models. A vendor key in `.env` outranks the local models; [Configuration](/en/configuration#local-models) has the three variables that reverse that.

## What leaves the machine {#what-leaves-the-machine}

Your record lives in your own Postgres, and nothing here reports usage anywhere. What leaves depends on who reads it:

| | With a model key | 100% on this machine |
| --- | --- | --- |
| Your documents and questions | Sent to that vendor, under its terms, except table rows read here by their headers | Stay here |
| A name to a code, a unit to UCUM (② Translate) | Here, from a bundle inside the package, with no network | The same |
| Model weights | None | Downloaded once from Hugging Face; `HF_ENDPOINT` in `.env` names a mirror |
| A device vendor (Garmin, Oura, Whoop) | Only after you link one: its tokens and your own data | The same |
| Container images | Pulled from Docker Hub, or from a mirror when it does not answer (`DOCKER_MIRROR=` in `.env` turns the mirror off) | The same, plus llama.cpp's image |
| Sign-in mail | Only once `EMAIL_SMTP_HOST` is configured: the address and the code, to your own mail server | The same |

Encryption at rest covers chat, uploaded files, medication text and your profile, not yet readings or genotypes. The app listens on `127.0.0.1` only; before it reaches a network you do not control, read <OssLink path="SECURITY.md" />, which lists every address the server can call.

## Export and backup {#export-and-backup}

Readings export as CSV or JSON, the visible record streams as NDJSON, genotypes export as VCF or FHIR, and `shell/backup.sh` makes the complete copy of the database and uploaded files. [Export Your Data](/en/deployment/export) has the routes and their limits.

## Contributing {#contributing}

The most useful contribution is a term the resolver gets wrong. Run `mirobody resolve "<term>"`; if the answer is wrong or empty, [report it](https://github.com/thetahealth/mirobody/issues), or add a row to <OssLink path="mirobody/res/loinc/resolver_overrides.tsv" /> together with a case in <OssLink path="mirobody/tests/test_engine_coverage.py" />. The full workflow is in <OssLink path="CONTRIBUTING.md" />; security reports go through a private advisory, as <OssLink path="SECURITY.md" /> describes.
