This procedure is for the Docker deployment described in [Deploy on a Server](/en/deployment/production). `deploy.sh` recreates any changed service in place (`docker compose up -d --remove-orphans`), which briefly interrupts the running stack, so reserve a maintenance window. Database schema changes are additive on startup; there is no automatic down migration. A code checkout alone is not a rollback. Upgrading from 1.5.2 removes Redis from the stack; see [Backup & Restore, "Upgrading from 1.5.2"](/en/deployment/backup#upgrading-from-152) for the extra steps that release needs. Upgrading to 1.5.4 drops the reading tables that 1.5.0 replaced; the one that held every reading before 1.5.0 goes only once `mirobody migrate-observations` has proven every row moved, and the release's notes in <OssLink path="CHANGELOG.md" /> say when to run it and with which flag.

## Before changing code

<Steps>
  <Step title="Record the running version">
    In the engine checkout, record the current commit and confirm the service responds:

    ```bash
    git rev-parse HEAD
    curl -fsS http://127.0.0.1:18060/api/health
    ```

    The health response includes a `version` field. Keep both values with the change record so you know exactly what you are returning to if a restore is needed.
  </Step>
  <Step title="Back up data and keys">
    Run the repository's backup script and move its output to storage off this host:

    ```bash
    shell/backup.sh
    ```

    The script backs up Postgres and local uploads when present; follow [Verify and Restore a Backup](/en/deployment/restore) for a scratch-database rehearsal and recovery steps. Preserve `.env`, your `config.prod.yaml` or other active overlay, any `.key.yaml` files, and `compose.override.yaml` in protected storage too. The script does not include those files. Keep any external object-storage bucket backed up separately.
  </Step>
  <Step title="Review the target release">
    Read the target version's notes in <OssLink path="CHANGELOG.md" /> and its release page. Confirm that your overlay keys and provider configuration still apply. Choose the exact release tag or commit; set `TARGET_REF` to that reviewed value in your shell before continuing.
  </Step>
</Steps>

## Upgrade and verify

<Steps>
  <Step title="Switch to the reviewed release">
    In the same checkout, fetch and inspect the selected ref, then check it out:

    ```bash
    git fetch --tags origin
    git show --no-patch "$TARGET_REF"
    git checkout "$TARGET_REF"
    ```

    Check `git status --short` first if you keep local changes in tracked files; Git will refuse a conflicting checkout.
  </Step>
  <Step title="Start the new stack">
    ```bash
    ./deploy.sh
    ```

    The script pulls the release image `compose.yaml` names (falling back to the `docker.1ms.run` mirror, or building locally from this checkout only when neither pull succeeds), then starts Postgres, the server and the worker, plus the one-shot container that fixes upload-volume ownership, and waits for them to report healthy. No Python dependencies install at boot; that only happens inside a local build. A stack that runs the local models keeps them: `COMPOSE_PROFILES` in `.env` starts the `llama` service again, and its models volume is reused, so nothing is downloaded a second time. Watch for startup or schema errors with `docker compose logs -f mirobody` in another terminal.
  </Step>
  <Step title="Check the result">
    In another terminal, run:

    ```bash
    docker compose ps
    curl -fsS http://127.0.0.1:18060/api/health
    ```

    `mirobody` should be healthy and the response's `version` should match the release you selected. Sign in through the public HTTPS address, open an existing record and verify one workflow your users depend on, such as file upload or an agent answer. If the service does not become healthy, use [Troubleshooting](/en/troubleshooting) and inspect `docker compose logs --tail 80 mirobody`.
  </Step>
</Steps>

## Rollback

Stop the app and worker, restore the database and any local uploads from the pre-upgrade backup, restore the **matching** keys and configuration, then return the checkout to the recorded commit and start it. Follow [Verify and Restore a Backup](/en/deployment/restore#recover-a-deployment) for the restore commands. Treat the backup as a unit: restoring only code after a schema change can leave the old release reading a newer database.
