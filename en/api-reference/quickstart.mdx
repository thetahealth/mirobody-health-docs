This first run uses `curl` and two **sample** readings. You will write them, confirm that they resolve to the same LOINC code, and ask a question about them. Allow about 10 minutes. The example keeps the readings for one hour; set an appropriate retention period for real data.

## Preparation

Create a `mb_live_*` key in the console for **the same region you will call**: [Global](https://platform.mirobody.ai/) or [China](https://platform.mirobody.cn/). Open **API Keys** and copy the secret when it appears; it is shown once. Set the matching API base URL and key in your shell. This example selects Global; for a China account, use the commented China line instead:

```bash
export MIROBODY_API_BASE="https://api.mirobody.ai/v1"   # Global
# export MIROBODY_API_BASE="https://api.mirobody.cn/v1" # China: use this instead
export MIROBODY_API_KEY="mb_live_..."
```

## Run the example

<Steps>
  <Step title="① Collect: write two sample readings">
    <IngestMentalModel />

    Write structured readings with [`POST /v1/data`](/en/api-reference/data). `retention` is **required**. Keep the same `user` value in every step so all calls address the same Subject.

    ```bash
    curl "$MIROBODY_API_BASE/data" \
      -H "Authorization: Bearer $MIROBODY_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
            "user": "docs-demo",
            "retention": "1h",
            "records": [
              {"indicator": "fasting_glucose", "value": 97, "unit": "mg/dL", "time": "2026-06-16T07:30:00Z"},
              {"indicator": "FBG",             "value": 92, "unit": "mg/dL", "time": "2026-06-17T07:25:00Z"}
            ]
          }'

    ```

    Expect a JSON response with `"status": "ok"`, `"ingested": 2`, and `"subject": "docs-demo"`. `standardized` tells you how many readings received a LOINC code. If you repeat this write, you create more rows: [writes are not idempotent](/en/api-reference/data#write-records).

    `user` is the [tenant-isolation key](/en/api-reference/overview#multi-tenancy-the-user-field). Use a stable, distinct id for each end-user in your application.
  </Step>

  <Step title="② Translate: it comes back coded">
    Note the two spellings above — `fasting_glucose` and `FBG`. Read the data back and both rows carry the **same LOINC code**, a canonical name, and UCUM-parsed values:

    ```bash
    curl "$MIROBODY_API_BASE/data?user=docs-demo&limit=10" \
      -H "Authorization: Bearer $MIROBODY_API_KEY"
    ```

    ```json
    {
      "object": "list",
      "data": [
        {
          "indicator": "FBG",
          "value": "92",
          "parsed_value": "92",
          "parsed_unit": "mg/dL",
          "loinc_code": "1558-6",
          "canonical_name": "Fasting glucose [Mass/volume] in Serum or Plasma",
          "time": "2026-06-17T07:25:00+00",
          "source": "api",
          "comment": ""
        },
        {
          "indicator": "fasting_glucose",
          "value": "97",
          "parsed_value": "97",
          "parsed_unit": "mg/dL",
          "loinc_code": "1558-6",
          "canonical_name": "Fasting glucose [Mass/volume] in Serum or Plasma",
          "time": "2026-06-16T07:30:00+00",
          "source": "api",
          "comment": ""
        }
      ],
      "has_more": false,
      "subject": "docs-demo"
    }
    ```

    On a fresh Subject, the response should include both names with the same `loinc_code`; IDs and other fields may vary. `value` is the original number as a string, and the parsed unit is separate. That's the [standardization pipeline](/en/api-reference/standardization): deterministic name→LOINC (no LLM code-guessing) + UCUM on every structured-record write.
  </Step>

  <Step title="③ Agent: get a grounded answer">
    Call the [Answers API](/en/api-reference/chat) with the **same** `user`. It can consult the rows you just wrote, including the one named `FBG`:

    ```bash
    curl "$MIROBODY_API_BASE/chat/completions" \
      -H "Authorization: Bearer $MIROBODY_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
            "model": "mirobody-flash",
            "user": "docs-demo",
            "messages": [{"role": "user", "content": "What fasting glucose readings did I add?"}]
          }'
    ```

    Read the answer in `choices[0].message.content`. `health_records` and `message.tool_steps` show which records and server tools were used; their content varies by run. For your own tool calls or conversation state, continue with the [Agent API](/en/api-reference/responses) and [SDK examples](/en/api-reference/sdk-examples). Pass the same Subject when using an agent SDK; otherwise it reads your account's default Subject.
  </Step>
</Steps>

## If a call fails

For `401`, check that the key and `MIROBODY_API_BASE` belong to the **same region**, then check the bearer header. For `400`, read `error.code` and `error.param` in the [error reference](/en/api-reference/overview#error-format). For `429`, follow [Rate Limits & Quota](/en/api-reference/rate-limits); a rate limit and an exhausted quota need different responses.

## Other data sources

For a lab report, upload a [PDF, photo or spreadsheet](/en/api-reference/files). For a synchronous preview of extracted readings, use [`POST /v1/standardize`](/en/api-reference/extract) with a file or an uploaded `file_key`. For device readings at scale, continue with [Structured Records](/en/api-reference/data). These paths share the same `user` isolation rule.

## The console Playground

The console Playground follows the same flow: **① Collect data → ② Auto-standardize → ③ Agent or Answers**. Upload a file, inspect the extracted text or standardized records, and run either API without writing code. Open the console for **your account's region**; usage is in its sidebar.
