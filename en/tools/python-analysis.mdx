Every chat model uses the same `python_exec` tool. A cloud model can generate
the code, while execution uses the application's local Docker daemon.
The calculator has no application mounts, database credentials or network.

The data path is the existing record tool's `Envelope` → `ToolMessage.artifact`
→ injected `ToolRuntime` → JSON in the local calculation container. The model
supplies code; it never needs to copy a compact display table into arguments.
Constant columns, nested rows, numeric JSON types, citation `rid`s and query
metadata remain available. Health indicators, medications, genetics and
pharmacogenomics use this same envelope path.

## Inputs and outputs {#inputs-and-outputs}

- `data`: the latest successful, nonempty record result's original rows.
- `results`: successful record envelopes from the current turn, including
  their `data`, `meta`, `tool`, `tool_call_id`, assumptions and provenance.
- `/workspace/data.json`: the same JSON object with `data` and `results`,
  available inside the computation. This is a container path, not an upload
  or library path for the agent's document tools.

The current turn begins at the latest user question; harness repair instructions
remain in that same turn. Failed or empty latest
lookups are refused rather than silently reusing earlier readings or turning
missing data into zero. Use the existing query `stats` and time-bucket views
for the aggregates they already provide; Python handles additional arithmetic
and comparisons across returned results.

Print the computed result and its source rids. The tool returns exit status,
output truncation and supplied source-call IDs as an artifact. A partial source
is disclosed before the output. Large tool text uses the harness's existing
filesystem offloading; output above the executor's 40,000-byte budget is
explicitly marked incomplete.

## Local setup {#local-setup}

Install the agent/application extra and prepare the local image:

```bash
pip install -e '.[app,test]'
docker pull python:3.12-slim
```

Docker Desktop or Colima on macOS and Docker Engine on Linux work through a
local Unix socket. The executor uses `PYTHON_SANDBOX_DOCKER_HOST`, then
`DOCKER_HOST`, then `/var/run/docker.sock` or the active Docker CLI context.
TCP/SSH Docker endpoints are rejected. Images are prepared locally; no cloud
sandbox account or execution API is used.

The default image offers Python's standard library. `PYTHON_SANDBOX_IMAGE`
can name a locally prepared image containing analysis libraries. Prepare its
dependencies before running: calculation containers have no network and
never receive application secrets.

When the app runs in Docker, it also needs access to the same machine's local
daemon. The opt-in [compose-python.yaml](https://github.com/thetahealth/mirobody/blob/4ed28c160af9ae0bede547880759e5570b2243df/compose-python.yaml) mounts that
management socket into the app; the calculation containers receive no socket.
This grants the app container-management authority, so the main Compose file
does not enable the mount automatically.

Set `PYTHON_DOCKER_SOCKET` to the socket path on the daemon host and
`PYTHON_DOCKER_GID` to its owning group ID, then include the overlay:

```bash
docker compose -f compose.yaml -f compose-python.yaml up -d
```

If a local executor is unavailable, the tool reports an execution setup
problem; the queried readings remain valid. Deployments using only query
views can hide the calculator with `DISALLOWED_TOOLS: [python_exec]`. The
prompt derives its computation capability from the actual tool list.

## Runtime and checks {#runtime-and-checks}

`LocalPythonSandbox` extends Deep Agents' `BaseSandbox`; the Docker SDK
provides its local transport and container lifecycle. The inherited filesystem
helpers and standard execution responses are reused. The model receives a
Python tool, with the broad native shell execution tool excluded. The existing
read-only document projections and single agent harness remain in place.

Each computation uses UID/GID 65534, a read-only image, container-owned tmpfs,
one CPU, 512 MB of memory, and a 64-process cap. Output is bounded while
streaming. Commands have a 1–30 second deadline; the host awaits execution for
that limit plus ten seconds and closes the stream/container on timeout or
cancellation. A finite container lease and automatic removal cover abandoned
containers after application termination; normal cleanup removes them sooner.

Run the original-data and local lifecycle checks with:

```bash
pytest -q tests/test_code_tool_capability.py tests/agent/test_code_tool_probe.py
```

These include constant and singleton rows, phased genotype strings, nested
annotations, multiple sources, partial metadata, output truncation and real
Docker timeout cleanup. The [language probe](https://github.com/thetahealth/mirobody/blob/4ed28c160af9ae0bede547880759e5570b2243df/benchmarks/local_agent/README.md)
uses synthetic records and the production Python tool. Its changed-data replay
checks calculations without more model requests.

The original `eval`/QuickJS interpreter, PTC bridge and per-model `code_tool` /
`eval_fetch` switches were removed. JavaScript remains only an optional Node
container in the comparison benchmark.

References: [Deep Agents sandbox architecture](https://docs.langchain.com/oss/python/deepagents/sandboxes#the-execute-method),
[local shell limitations](https://docs.langchain.com/oss/python/deepagents/backends#localshellbackend-local-shell).
`LocalShellBackend` does not isolate code from an application's files; this
service uses a local container boundary while reusing the backend interface.
