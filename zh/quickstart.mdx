## A · 这个库 {#a--这个库}

解析器使用建在 LOINC 上的词法索引，唯一的依赖是 numpy，不需要模型、API Key 或数据库。[安装 uv](https://docs.astral.sh/uv/getting-started/installation/) 后，无需克隆仓库或手动管理 Python 环境，就可以试用：

```bash
uvx --python 3.12 mirobody resolve "LDL cholesterol" 血红蛋白 ヘモグロビン "空腹血糖(GLU)" 血脂
```

uv 会按需下载 Python，并在隔离环境里准备依赖包。首次下载需要联网，之后名称和单位解析可以离线完成。`--python 3.12` 用来选定受支持的解释器。

<p align="center">
<img src="/images/oss/docs/images/resolve-demo.zh-CN.gif" alt="mirobody resolve：血红蛋白 和 ヘモグロビン 落到同一个 LOINC 码上，还有一次刻意的弃答" width="880" />
</p>

`血脂` 说的是一个类别，不是一项具体的观测，所以它什么都解析不到。这是故意的设计：一个错的码会把两种不同的检验放进同一条趋势线。

要集成到自己的 Python 3.12+ 环境中，先安装这个库：

```bash
pip install mirobody
```

Python 调用的是同一个引擎。单位是一条读数身份的一部分，所以它能改变编码：

```python
from mirobody.engine import resolve, resolve_reading, standardize_reading

resolve("血红蛋白").loinc                                     # '718-7'   任何语言，同一个编码
resolve("total cholesterol").loinc                          # '2093-3'  [Mass/volume]
resolve_reading("total cholesterol", "5.0", "mmol/L").loinc  # '14647-2' [Moles/volume]：单位决定编码
resolve_reading("中性粒细胞", "62 %", None).loinc              # '26511-6' 一个百分比……
resolve_reading("中性粒细胞", "4.2", "10*9/L").loinc           # '26499-4' ……和一个计数，是两个编码
standardize_reading("血红蛋白", "13.5", "g/dL")["code"]["coding"][0]["code"]  # '718-7'  作为一条 FHIR Observation
```

主诉和诊断有自己的轴，ICPC-3，规则一样：要么给出一个编码，要么给出明确的拒绝理由，不猜。

```python
from mirobody.translate import resolve_symptom, resolve_condition

resolve_symptom("头疼").code           # 'NS01'         头痛；'headache' 和 '頭痛' 得到同一个结果
resolve_symptom("疼").outcome         # 'refused'      太宽泛，编不了码；原话被保留
resolve_condition("2型糖尿病").code    # 'TD72'         2型糖尿病
resolve_condition("糖尿病").outcome    # 'needs-input'  哪一型？会问，不会猜
```

读一份厂商导出的文件不需要其他依赖；`zipfile` 和 `xml.etree` 都是标准库：

```bash
mirobody import apple ~/Downloads/export.zip
```

剩下的部分：`pip install 'mirobody[parse]'` 能把一份 PDF、照片或表格变成读数（这一步会调用模型，所以需要一把 Key），`pip install 'mirobody[app]'` 安装服务端。以上内容都不需要它们。`[agent]` 是把 agent harness 作为库使用，`[test]` 是测试套件。

不用整套服务，`uvx --python 3.12 mirobody mcp` 就能通过 stdio 把词表交给一个 MCP 客户端，离线、不需要 Key。它唯一那个读整份文档的工具，`standardize_report`，还需要 `[parse]` 这个 extra 和一把模型 Key。[standardization.zh-CN.md](/zh/concepts/indicators) 详细讲了 ② 转译，[`examples/`](https://github.com/thetahealth/mirobody/blob/4ed28c160af9ae0bede547880759e5570b2243df/examples/README.md) 里有可以直接运行的脚本。

## B · 整套服务 {#b--整套服务}

完整应用包含网页客户端、带 pgvector 的 Postgres、服务端和后台任务，并预置一份合成示例记录。先选择运行在哪里。

<a id="try-it-in-codespaces"></a>

### 在 Codespaces 体验 {#在-codespaces-体验}

[![在 GitHub Codespaces 中打开](https://github.com/codespaces/badge.svg)](https://codespaces.new/thetahealth/mirobody?quickstart=1)

用你的 GitHub 账号创建 Codespace，不需要在本机安装 Docker 或 Python。等待终端中的自动设置完成，再打开它打印的 HTTPS 设置链接。填入你自己的模型 API Key，例如 [OpenRouter](https://openrouter.ai/keys) 或 [OpenAI](https://platform.openai.com/api-keys)。设置页会发送一次真实请求，验证通过后才保存 Key。应用默认使用仅自己可访问的 `18060` 转发端口。

在「邮箱验证码」标签使用 `you@mirobody.ai`、验证码 `111111` 登录，问「我的胆固醇有什么变化？」。再到「数据」页上传 [`demo/upload/`](https://github.com/thetahealth/mirobody/tree/4ed28c160af9ae0bede547880759e5570b2243df/demo) 里的一份合成样例，体验文档处理。

应用和存储的记录位于 GitHub 云端，需要模型处理的文档和问题会发送给你选择的模型服务商。体验时请使用随仓库提供的合成数据。[Codespaces 的使用与计费规则](https://docs.github.com/en/billing/concepts/product-billing/github-codespaces) 和模型服务商的收费规则分别适用。体验结束后请停止 Codespace；再次打开时，部署脚本会重新运行，启动应用。

<a id="run-it-100-locally"></a>

### 100% 在本机运行 {#100-在本机运行}

不需要模型 API Key。带 Compose 的 Docker 会同时启动应用和 llama.cpp 的 CPU 服务，由它运行回答模型和文档识别模型：

```bash
git clone --depth 1 https://github.com/thetahealth/mirobody.git && cd mirobody
COMPOSE_PROFILES=local-cpu ./deploy.sh
```

建议主机有 16 GB 内存，至少分配 8 GB 给 Docker。不需要显卡；Windows 用户请在 WSL 2 终端执行。首次启动需要下载容器镜像和模型权重；下载完成后，应用、模型、记录和文档处理都留在本机。CPU 回答可能需要几分钟；[local-models.zh-CN.md](/zh/local-models) 有 GPU 和 Mac 的配置方案。打开脚本打印的应用链接，使用下面的示例账号登录。

`deploy.sh` 会生成密钥写进 `.env`，并拉取预构建镜像；镜像里已经带着 LOINC 词表，所以 Docker 用户不需要 Git LFS。主机需要 Git 和 OpenSSL。本地 profile 会自动选好本地模型。

**如果希望在 Docker 中使用云端模型，** 不启用本地 profile，改为运行 `./deploy.sh`。打开它打印的 `http://localhost:18060` 设置链接，填入一把模型 API Key。应用和记录留在你自己的主机上，需要模型处理的文档和问题会发送给模型服务商。

在「邮箱验证码」标签用 `you@mirobody.ai`、验证码 `111111` 登录；不涉及任何邮件服务商。`SEED_DEMO_DATA` 默认打开，所以两个账号下已经有 2,019 条读数。如果打算保存真实数据，请在第一次启动前把它设为 `false`，这样两个账号都不会被创建。[`demo/upload/`](https://github.com/thetahealth/mirobody/tree/4ed28c160af9ae0bede547880759e5570b2243df/demo) 里的四份文件是刻意没有播种进去的，所以把其中一份拖到 Data 页走的是真实路径。

一把 Key 也可以不填在设置页，而是写进 `.env`：`OPENROUTER_API_KEY`、`OPENAI_API_KEY`、`GOOGLE_API_KEY`、`ANTHROPIC_API_KEY`，或者通过 `<PROVIDER>_BASE_URL` 指向任何 OpenAI 兼容网关。写完之后运行 `docker compose up -d`；`restart` 不会重新读取 `.env`。[`config.llm.yaml`](https://github.com/thetahealth/mirobody/blob/4ed28c160af9ae0bede547880759e5570b2243df/config.llm.yaml) 里写的是每个条目读取哪个变量名（`api_key: OPENROUTER_API_KEY`），从不写密钥本身。要查看每个模型环节选用了哪个条目：

```bash
docker compose exec mirobody mirobody doctor          # 加上 --probe 会给每一个发送一次真实请求
```

[自部署指南](/zh/self-host) 按步骤讲解整个过程，[walkthrough.zh-CN.md](/zh/walkthrough) 带你把运行中的服务走一遍。

## C · 一份检出 {#c--一份检出}

`serve` 是部署的形态：它读取随包的配置和任何 `config.{ENV}.yaml` 覆盖层，并要求持久的密钥。`dev` 在一个进程里运行同一个服务端，用的是内存里的配置和临时生成的密钥：

```bash
git clone --depth 1 https://github.com/thetahealth/mirobody.git && cd mirobody
git lfs install && git lfs pull
python3.12 -m venv .venv && . .venv/bin/activate
pip install -e '.[app]'
```

如果手头还没有带 pgvector 的 Postgres，先启动一个：

```bash
docker run -d -p 5432:5432 -e POSTGRES_USER=user -e POSTGRES_PASSWORD=pw \
    -e POSTGRES_DB=mirobody \
    pgvector/pgvector:pg17
```

**这一步并不需要 `docker`。** 在 Debian 或 Ubuntu 上，`scripts/install_native.sh` 会用发行版自己的仓库装好 PostgreSQL 和 pgvector，启动集群，建好角色和数据库，再把包装进一个 virtualenv。在 Ubuntu 24.04 上实测，那里的 pgvector 是 0.6.0，上面的 `CREATE EXTENSION vector` 可以满足。之后 `scripts/start_native.sh` 会启动 worker 和 server（端口 18060），并打印打开它的地址。

然后启动 API；如果用的是已有的数据库，替换掉连接地址。再开一个终端检查它的健康检查端点：

```bash
mirobody dev --pg-url postgres://user:pw@localhost:5432/mirobody
```

```bash
curl -fsS http://127.0.0.1:18090/api/health
```

返回内容里带一个 `version` 字段。请用 pgvector 而不是普通 Postgres：schema 首次启动时会建一个 vector 列。

**在仓库根目录运行 `dev`，它同时提供网页客户端。** 构建好的客户端放在仓库根目录的 `frontend/`，在包之外，所以一份检出里有它、`pip install` 里没有。`utils/config/http.py` 只要发现工作目录下存在 `frontend/` 就挂载它，因此在仓库根目录下，同一个地址同时提供 API、MCP 接口、agent 和界面。本页此前写的是相反的结论，实测后改正：从仓库根目录访问 `GET /` 返回的是构建好的页面，只有在检出目录之外做 `pip install` 时才只剩 API。

`dev` 生成的密钥是每次运行各不相同的：会话和加密过的配置值在重启后不会保留。要保留它们，请在环境变量里设置 `JWT_KEY` 和 `CONFIG_ENCRYPTION_KEY`。

## 没有出现时 {#没有出现时}

| 你看到的                                                   | 原因                                                                                                                                       |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `mirobody doctor` 显示 `keys present : none`，每个环节都是 `--` | 没有模型 Key，也没有本地模型服务。① 收集和 ② 转译仍然能用；抽取和回答不行。打开 `./deploy.sh` 打印出来的链接。                                                                      |
| 在一份新克隆上查 LOINC 会报错                                     | `git lfs pull` 还没有运行过，词表还只是一个指针占位文件。                                                                                                     |
| `mirobody dev` 退出并要求提供 Postgres                        | 给出 `--pg-url`，或者在环境变量里设 `PG_URL` / `DATABASE_URL`。                                                                                       |
| 服务端启动了，但设备同步一直没有运行                                     | 检查后台任务的日志和 Postgres 连接；设备拉取和任务状态都用 Postgres。                                                                                             |
| `mirobody serve` 连不上 Postgres                          | 为那个数据库设置 `PG_HOST`、`PG_PORT`、`PG_USER`、`PG_PASSWORD` 和 `PG_DBNAME`。                                                                      |
| 拉镜像卡住，或 `deploy.sh` 报 Docker Hub 不可达                   | `deploy.sh` 会测试守护进程到镜像仓库的连通性，不通时把 `DOCKER_MIRROR=<registry>/` 写进 `.env`，重试就走镜像站，并会说明这件事。手动设置同一个键可以指定你自己的站点；它会作为前缀加到每个镜像上，本地构建用的基础镜像也算在内。 |
